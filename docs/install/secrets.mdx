---
title: Secrets and keys
description: How Lembos creates, keeps and rotates its secrets, and what to back up.
---

You do not have to create any secrets to install Lembos. A **setup job** runs before every install and
upgrade and makes sure each one exists.

## Where each secret comes from

For every secret, in order:

1. **A Secret you manage** — named with `existingSecret`, for instance from Sealed Secrets, External
   Secrets or SOPS. Lembos leaves it alone.
2. **A value in your values file**, which the job writes.
3. **The value already in the cluster**, which the job keeps.
4. **Generated** by the job.

Nothing is rotated by an upgrade. To rotate a value, delete that key (or the whole Secret) and upgrade.

## What is in them

The release's Secret, `lembos-secrets`, holds the client secrets of the Portal, the Orchestrator and the Temporal UI,
a **key pair for each of the platform's machine accounts** — the private key it signs its token requests with, and the
public half Identity checks them against, derived from it on every run — Identity's encryption key, the **bootstrap
administrator's password**, and the PostgreSQL and Redis passwords.

Four key pairs sit beside it: the key Identity signs tokens with, and the certificates that protect each
service's sign-in key ring. Self-signed pairs are right for all four. If you issue them with cert-manager,
use a long duration and never rotate the private key.

The job also issues the certificates that encrypt traffic inside the installation, each with a CA of its
own whose key it does not keep:

| Secret                       | What it is                                                             |
|------------------------------|------------------------------------------------------------------------|
| `lembos-service-tls`         | What every Lembos service serves HTTPS with                            |
| `lembos-temporal-tls`        | What Temporal's frontend serves                                        |
| `lembos-temporal-client-tls` | What the services present to Temporal, which refuses anyone without it |
| `lembos-redis-tls`           | What HAProxy serves in front of a high-available Redis                 |

Each CA's certificate is in a `-ca` Secret beside them, for the callers that verify it. These can be
renewed: delete a certificate's Secret and its CA's and upgrade, and the job issues the set again. Or issue
them with cert-manager and name them in `listeners.existingSecret` and `temporal.tls.existingSecret`.

A Temporal Cloud API key is never generated; give it in your values or in a Secret you manage. The mail relay's
password is a declared credential's secret, below.

### Credentials you declare

A credential your installation owns — your organisation's GitHub App, a token for your registry, the AWS role every
team's accounts are reached through, the relay your mail leaves through — can be declared in your values instead of
registered in the Portal, under `platform.integrations.credentials.<name>`, with its type, who it is and the URL
prefixes it opens:

```yaml
platform:
  integrations:
    credentials:
      github:
        type: GitHubApp
        appId: "123456"
        uses:
          sourceAccess:
            Git: [https://github.com/acme]
secrets:
  credentials:
    github:
      existingSecret: lembos-github-app   # holding credential-github-secret, the app's PEM key
```

Its secret, `credential-<name>-secret`, is never generated: give it inline as `secret` or in a Secret you manage. It
reaches the Orchestrator alone, which keeps it in memory and never in its database. The credential appears in the
Portal as `platform/github` (or in the `namespace` its entry names), read-only; to rotate it, change the secret and
restart the Orchestrator, which checks it again as it starts — and every target that names it.

A role is assumed with the Orchestrator's own identity, so it has no secret to give:

```yaml
platform:
  integrations:
    credentials:
      aws:
        type: AwsRole
        roleArn: arn:aws:iam::123456789012:role/lembos-deployer
        externalId: lembos   # only if the role's trust policy asks for one
        # endpointUrl: only for an emulator, where STS is asked
```

Any team's target can name it, since the Platform group owns it unless `owner` says otherwise. While a target names it,
the Orchestrator will not start without it: give those targets another credential before removing the entry.

To post notifications in Slack, declare your workspace's Lembos app — created in Slack with the bot scopes `chat:write`,
`channels:read`, `groups:read` and `users:read`, and installed — with its bot token as the secret. Marked
`uses.notifications`, it makes Slack a channel people and groups can choose beside email:

```yaml
platform:
  integrations:
    credentials:
      slack:
        type: SlackApp
        uses:
          notifications: true
secrets:
  credentials:
    slack:
      existingSecret: lembos-slack   # holding credential-slack-secret, the app's xoxb- token
```

Everything Lembos mails — invitations, address confirmations, password resets, connection codes and notification
email — leaves through one relay, declared as an `SmtpRelay` marked `uses.mail`. Its `url` is `smtp://host:port`, or
`smtps://` for TLS from the first byte; `security` is `StartTls` unless it says `Tls`, or `None` for a mail catcher,
which never takes a login. The secret is the login's password, and a relay without a `username` has none. Marked
`uses.notifications` too, it makes email a channel people and groups can choose; without it, it still sends account
mail and codes:

```yaml
platform:
  integrations:
    credentials:
      mail:
        type: SmtpRelay
        url: smtp://relay.example.com:587
        username: lembos@example.com
        uses:
          mail: true
          notifications: true
secrets:
  credentials:
    mail:
      existingSecret: lembos-smtp   # holding credential-mail-secret, the login's password
```

Outside Development the install refuses a relay reached in clear or without a login. The Orchestrator hands the relay
to the Worker for each message, and checks it by connecting and signing in, sending nothing — its page in the Portal
says whether mail can leave.

## Back them up

<Callout type="warn">
  Losing a generated secret is not recoverable: tokens, sessions and stored credentials are all encrypted
  under them. Back up every Secret labelled `app.kubernetes.io/managed-by: lembos-setup`.
</Callout>

`helm uninstall` deliberately leaves these Secrets behind, so reinstalling into the same namespace picks
them up again. Deleting the namespace removes them.

## Verifying the images

Every Lembos image is signed when it is published, and the signature is recorded in the public Rekor
transparency log. Verify by digest rather than by tag — a tag can move after signing:

```bash
cosign verify \
  --certificate-identity-regexp '^https://github.com/lembosproj/platform/\.github/workflows/release\.yml@refs/heads/main$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/lembosproj/platform/orchestrator@sha256:<digest>
```

An admission controller that checks signatures, such as Kyverno or Sigstore's policy controller, takes the
same two values.
