---
title: Publish from CI
description: Register every build your pipeline pushes as an artifact of its component, with its provenance.
---

A component ships **artifacts**: the builds a release carries from environment to environment. The platform
learns about a build when your pipeline tells it, right after the push, so nobody has to type a digest into
the Portal. Each build is registered by its content digest, labelled by its tag, and records where it came
from: the repository, commit, ref and CI run. It then appears on the component's **Artifacts** tab, ready
for a release.

There is a ready-made step for three CI systems, each running the same program:

| CI system       | Use                                                                                                                        |
|-----------------|----------------------------------------------------------------------------------------------------------------------------|
| GitHub Actions  | The [publish-artifact action](https://github.com/lembosproj/platform/tree/main/src/Integrations/GitHub/publish-artifact)   |
| GitLab CI/CD    | The [publish-artifact template](https://github.com/lembosproj/platform/tree/main/src/Integrations/GitLab), included by URL |
| Azure Pipelines | The [publish-artifact steps template](https://github.com/lembosproj/platform/tree/main/src/Integrations/AzureDevOps)       |

Any other CI system can make the same call to the API; see [The call itself](#the-call-itself).

## 1. Get a service account

A pipeline signs in as a [service account](/docs/use/access#service-accounts), never as a person. Ask an
Administrator for one per CI system, for example one for your GitHub organisation or your GitLab group. It
needs:

| What      | Set to                                                                                                                                                                                                |
|-----------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Owner** | The team that owns the components the pipeline builds, or a group above all of them. Owning gives the account reach over that group's subtree, and publishing needs reach over the component's owner. |
| **Role**  | **Maintainer**, or a custom role with `infrastructure:artifacts:write`, `infrastructure:artifacts:read` and `catalog:components:read`.                                                                |

Creating the account downloads its private key once, as `<client id>.pem`. Lembos keeps only the public
half. An account given a public key you generated yourself takes that pair's private key instead: RSA, or
ECDSA on P-256, P-384 or P-521.

<Callout type="warn">
An account reaches what its owning group reaches. If one pipeline builds components of two teams with no
group above them, it gets a second account, not a wider one.
</Callout>

## 2. Store the key in your CI system

Each CI system keeps four values: the account's client id and private key, which are secret, and the
platform's two addresses, which are not. Set them once where every repository that publishes can use them.

<Tabs groupId="ci" persist items={["GitHub Actions", "GitLab", "Azure Pipelines"]}>
<Tab value="GitHub Actions">

Add two secrets to the repository, or to the organisation so every repository can use them:

| Secret               | Value                                               |
|----------------------|-----------------------------------------------------|
| `LEMBOS_CLIENT_ID`   | The account's client id                             |
| `LEMBOS_PRIVATE_KEY` | The whole `.pem` file, BEGIN and END lines included |

Keep the addresses as variables, `LEMBOS_IDENTITY_URL` and `LEMBOS_ORCHESTRATOR_URL`. Set at the
organisation, with access for the repositories that publish, all four are configured once.

</Tab>
<Tab value="GitLab">

Add four CI/CD variables to the group that holds the projects that publish, under **Settings → CI/CD →
Variables**. Every project in the group inherits them.

| Variable                  | Value                                      | Visibility        |
|---------------------------|--------------------------------------------|-------------------|
| `LEMBOS_CLIENT_ID`        | The account's client id                    | Masked            |
| `LEMBOS_PRIVATE_KEY`      | The `.pem` file base64-encoded on one line | Masked and hidden |
| `LEMBOS_IDENTITY_URL`     | The Identity Server's address              | Visible           |
| `LEMBOS_ORCHESTRATOR_URL` | The Orchestrator API's address             | Visible           |

GitLab masks only a value on one line without spaces, which a `.pem` file is not. Encode it with
`openssl base64 -A -in <client id>.pem`; the step reads either form. Mark the variables **Protected** and
only pipelines on protected branches and tags can publish.

</Tab>
<Tab value="Azure Pipelines">

Add a variable group under **Pipelines → Library**, open to the pipelines that publish:

| Variable                  | Value                                      | Secret |
|---------------------------|--------------------------------------------|--------|
| `LEMBOS_CLIENT_ID`        | The account's client id                    | no     |
| `LEMBOS_PRIVATE_KEY`      | The `.pem` file base64-encoded on one line | yes    |
| `LEMBOS_IDENTITY_URL`     | The Identity Server's address              | no     |
| `LEMBOS_ORCHESTRATOR_URL` | The Orchestrator API's address             | no     |

A secret is typed on one line, which a `.pem` file is not. Encode it with
`openssl base64 -A -in <client id>.pem`; the step reads either form.

</Tab>
</Tabs>

## 3. Add the step after your push

<Tabs groupId="ci" persist items={["GitHub Actions", "GitLab", "Azure Pipelines"]}>
<Tab value="GitHub Actions">

```yaml
- id: build
  uses: docker/build-push-action@v6
  with:
    push: true
    tags: ghcr.io/acme/apps/order-api:${{ github.sha }}

- uses: lembosproj/platform/src/Integrations/GitHub/publish-artifact@v0.3.0
  with:
    client-id: ${{ secrets.LEMBOS_CLIENT_ID }}
    private-key: ${{ secrets.LEMBOS_PRIVATE_KEY }}
    identity-url: ${{ vars.LEMBOS_IDENTITY_URL }}
    orchestrator-url: ${{ vars.LEMBOS_ORCHESTRATOR_URL }}
    component: ordering/order-api
    repository: ghcr.io/acme/apps/order-api
    digest: ${{ steps.build.outputs.digest }}
    tag: ${{ github.sha }}
```

GitHub hands an action only the secrets and variables named on its step, so the four are named there. The
step's outputs are `artifact-id` and `coordinate`.

</Tab>
<Tab value="GitLab">

```yaml
include:
  - remote: https://raw.githubusercontent.com/lembosproj/platform/v0.3.0/src/Integrations/GitLab/publish-artifact.yml
    inputs:
      version: v0.3.0
      needs: [build]
      component: ordering/order-api
      repository: $CI_REGISTRY_IMAGE/order-api
      digest: $IMAGE_DIGEST
      tag: $CI_COMMIT_SHORT_SHA

build:
  stage: build
  script:
    - docker buildx build --push --metadata-file meta.json --tag "$CI_REGISTRY_IMAGE/order-api:$CI_COMMIT_SHORT_SHA" .
    - echo "IMAGE_DIGEST=$(jq -r '."containerimage.digest"' meta.json)" > build.env
  artifacts:
    reports:
      dotenv: build.env
```

The template adds a job, `publish-artifact`, which waits for the jobs in `needs` and takes the digest from
their dotenv report. Give the release tag twice, in the URL and as `version`: GitLab does not tell an
included file where it was included from. The job leaves `LEMBOS_ARTIFACT_ID` and `LEMBOS_COORDINATE` in
a dotenv report of its own. It runs on Linux runners, in an image with glibc, `bash`, `curl` and `jq`; the
default installs the last two each run.

</Tab>
<Tab value="Azure Pipelines">

```yaml
resources:
  repositories:
    - repository: lembos
      type: github
      name: lembosproj/platform
      ref: refs/tags/v0.3.0
      endpoint: github

variables:
  - group: lembos

steps:
  - bash: |
      docker buildx build --push --metadata-file meta.json --tag acme.azurecr.io/apps/order-api:$(Build.BuildNumber) .
      echo "##vso[task.setvariable variable=IMAGE_DIGEST]$(jq -r '."containerimage.digest"' meta.json)"
    displayName: Build and push

  - template: src/Integrations/AzureDevOps/publish-artifact.yml@lembos
    parameters:
      version: v0.3.0
      component: ordering/order-api
      repository: acme.azurecr.io/apps/order-api
      digest: $(IMAGE_DIGEST)
      tag: $(Build.BuildNumber)
```

`endpoint` is a GitHub service connection, which Azure Pipelines reads the template's repository through.
Give the release tag twice, in `ref` and as `version`: a template is not told the ref it was read at. The
service account and addresses default to the group's variables. The step sets the output variables
`LEMBOS_ARTIFACT_ID` and `LEMBOS_COORDINATE`, read as `$(lembos.LEMBOS_ARTIFACT_ID)`.

</Tab>
</Tabs>

`component` is the qualified name the Portal shows, which stays the same from one installation to the
next. `type` defaults to `OciImage`; `HelmChart` and `Archive` are the others. Each step's README lists
every input and output.

Pin the step to the tag of the platform release you run. Each release publishes the program the steps
run, built against that release's API. The step downloads it for the runner, Linux or Windows on x64 or
ARM64, and checks it against the release's digest, so the job needs no .NET or other setup.

## What happens on a run

- **Re-runs are safe.** If the component already has this digest, the step succeeds and returns the
  artifact registered the first time, with that run's provenance.
- **One digest, one component.** If the same bytes are registered to another component, the step fails and
  names it. To ship one build as several components, push it to a repository for each. One push to several
  repositories keeps the digest the same.
- **Refusals carry the platform's words.** The step fails with the API's own error in the log, and on
  GitHub and Azure Pipelines as an error on the run's summary too: a missing permission, a group the
  account does not reach, an unknown component or type, or a digest that is not one.

## The call itself

Without a ready-made step, a pipeline [obtains a token](/docs/use/access#obtaining-a-token) for the account
and sends one mutation to `https://<orchestrator>/graphql`:

```graphql
mutation {
  publishArtifact(input: {
    componentId: "<the component's id>"
    type: "OciImage"
    repository: "ghcr.io/acme/apps/order-api"
    digest: "sha256:…"
    tag: "1.4.2"
    provenance: {
      sourceRepository: "https://github.com/acme/apps"
      sourceCommit: "<commit>"
      sourceRef: "refs/heads/main"
      buildRef: "<the run's URL>"
    }
  }) { id coordinate }
}
```

`ownerId` may be left out; the artifact then belongs to the component's owner. To go from a name to an id,
ask `componentByName(name: "ordering/order-api") { id }` first.
