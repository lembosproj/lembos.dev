## Users

People join by **invitation**, or by signing in with GitHub if
[the integration](/docs/install/github) is on. Nobody registers themselves.

## Groups

A **group** is a team, a department or a project. Groups nest, and they **own** everything in Lembos:
every system, component, blueprint, environment and policy has an owning group.

Membership is how people reach things. A member of a group reaches what that group owns, and what every
group beneath it owns.

<Screenshot name="groups" ratio={2.6} alt="The groups: squads, tribes and the engineering organisation, each with its parent and number of members." />

## Roles

A **role** is a named set of permissions: *may this person do this kind of thing at all?* Lembos ships
three roles for people:

| Role              | For                                                                                   |
|-------------------|---------------------------------------------------------------------------------------|
| **Contributor**   | Product teams: describe software in the catalog, request runs, assemble and promote releases |
| **Maintainer**    | Platform teams: blueprints, execution targets, environments, placement rules and policies — and approving other people's runs |
| **Administrator** | Everything a person can do, including managing users, groups, roles and service accounts |

You can create your own roles. See [Built-in roles](/docs/reference/roles) for details.

<Screenshot name="roles" ratio={2.6} alt="The roles: the built-in Administrator, Contributor and Maintainer, and the machine-only roles, each with its permission count." />

Roles and ownership work together: a Contributor can deploy only what their groups own. And
[policies](/docs/use/governance) add the last check — whether this particular change is allowed now.

## Service accounts

A **service account** is a machine: a CI pipeline, an integration, an agent. It holds roles like a person,
but is never a member of a group. Instead it is granted reach over named group subtrees explicitly, so it
does not change when teams are reorganised.

When a service account acts on a person's behalf, it can do only what *both* of them may do.

<Screenshot name="service-accounts" ratio={2.8} alt="The service accounts: the platform's own agents, each with what it does, whether it acts on its own or only for a person, its reach and its status." />

Maintainers and Administrators can see each service account's roles, effective permissions and reach.

Lembos ships with its own service accounts, which run its background work and are only ever narrowed or
widened in where they reach. An Administrator creates the others: one per CI system or integration, owned
by the team it serves and reaching what that team owns from the start. The account's page says when
Identity has confirmed its credential, usually within seconds; a token request made before that is refused.
From the same page an Administrator assigns roles (the ones a person could hold) and archives the account,
which revokes everything it holds.

An account proves itself with a **key pair**, the way a GitHub App does. Creating one mints the pair and
downloads the **private key once**, as a PEM file named after the client id; Lembos keeps only the public
half, so there is nothing stored to leak and nothing to show again. Put the file where the system that
will use it can read it, and nowhere else. To rotate, choose **Rotate key** on the account's page: a new
pair is minted and downloaded while the old keys keep working, so switch the system to the new key and
then remove the old one from the page. An account in service always keeps at least one key, and holds at
most five.

One thing is available through the API rather than the Portal: giving an account a public key you generated
yourself (RSA from 2048 bits or ECDSA on P-256, P-384 or P-521), so the private key never leaves your
system. There is no shared-secret option for a service account; the platform's own machines authenticate
with keys too, and the only client secrets Lembos keeps are for its own web applications.

### Obtaining a token

A machine uses the `client_credentials` grant at the Identity Server's token endpoint,
`https://<identity>/connect/token`, with `scope=platform`, and authenticates with a signed **client
assertion** rather than a secret:

| Claim or header | Value                                                             |
|-----------------|-------------------------------------------------------------------|
| `typ` (header)  | `client-authentication+jwt`                                       |
| `alg` (header)  | `RS256` for an RSA key; `ES256`, `ES384` or `ES512` for ECDSA     |
| `kid` (header)  | The key id shown on the account's page                            |
| `iss` and `sub` | The client id                                                     |
| `aud`           | The Identity Server's issuer URL, exactly as it serves it         |
| `jti`           | A fresh random id per assertion                                   |
| `iat` and `exp` | Now, and a few minutes later — an assertion is single-use and short |

```bash
# An RS256 assertion with openssl alone; any JWT library does the same in one call.
b64() { openssl base64 -A | tr '+/' '-_' | tr -d '='; }
now=$(date +%s)
header=$(printf '{"alg":"RS256","typ":"client-authentication+jwt","kid":"%s"}' "$KEY_ID" | b64)
claims=$(printf '{"iss":"%s","sub":"%s","aud":"%s","jti":"%s","iat":%d,"exp":%d}' \
  "$CLIENT_ID" "$CLIENT_ID" "$ISSUER" "$(uuidgen)" "$now" "$((now + 300))" | b64)
signature=$(printf '%s.%s' "$header" "$claims" | openssl dgst -sha256 -sign private.pem | b64)

curl -s "$ISSUER/connect/token" \
  -d grant_type=client_credentials \
  -d scope=platform \
  -d client_id="$CLIENT_ID" \
  -d client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer \
  -d client_assertion="$header.$claims.$signature"
```

The reply's `access_token` is a bearer token for the Orchestrator's API, good for a few minutes; ask for
another rather than keeping one. The token endpoint budgets requests per client as well as per address, so
a job that retries in a tight loop is told to slow down with a `429` and a `Retry-After`.

The Orchestrator budgets what each caller asks of it, too — every caller outside the platform, a service
account or somebody's script alike:

| Budget        | Per minute, by default                                          | Chart value                                |
|---------------|-----------------------------------------------------------------|--------------------------------------------|
| Query cost    | 300,000, summed from each query's cost; a query is at least 100 | `orchestrator.rateLimit.queryCost`         |
| Changes       | 120, one per mutation field in a request                        | `orchestrator.rateLimit.mutations`         |
| Subscriptions | 30 opened                                                       | `orchestrator.rateLimit.subscriptionOpens` |

Over one, a request is refused with the error code `RATE_LIMITED` and a `retryAfter` in seconds, and over
HTTP with a `429` and a `Retry-After`; a request sent as `application/json` gets the same error with a
`200`. Each replica of the Orchestrator counts for itself. The Portal and the platform's own accounts are not
budgeted, and an operator can leave an integration they trust out by its client id, in
`orchestrator.rateLimit.exemptClients`.
