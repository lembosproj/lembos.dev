A golden path in Lembos is a **blueprint**: a versioned recipe for building a component, a resource or an
environment. Platform teams write them once; product teams use them without having to learn what is
underneath. Find them under **Platform**.

## Where things run: execution targets

An **execution target** is somewhere Lembos is allowed to build into — a cloud account, an on-premises
site, a Kubernetes cluster. Registering one is a deliberate act by the platform team; a blueprint can never
create one.

Today a target is one of three kinds. An **AWS account** is where Terraform blueprints build; a **Kubernetes
cluster**, or an **on-premises site** (a cluster whose hardware you own), is where Helm blueprints deploy.
Azure subscriptions and GCP projects are listed where a target is registered and cannot be registered yet.

<Screenshot name="execution-targets" ratio={2.3} alt="The execution targets: Kubernetes clusters and AWS accounts, each with its provider, whether it is reachable, its type and its capabilities." />

A target holds no secret of its own: it names the **credential** it authenticates with — an AWS access key, a
role Lembos assumes, or the identity the worker runs as for an account; a kubeconfig, a service account token or a
client certificate for a cluster or a site. It can name one its own group owns, or one a group above it provides —
the platform team's AWS role for every team's accounts, say — or register a new one in the same sheet.

Lembos checks the connection the moment a target is registered or changed, and on request, so a wrong role
or an expired credential shows up on the target rather than on the next deployment. A target's page shows
where it is, which credential gets the platform in, and when that was last checked.

<Screenshot name="execution-target" ratio={2.1} alt="An AWS account registered as an execution target, showing its account and state backend, its static-key credential verified as reachable, and a Check now action." />

## Credentials

A **credential** is how Lembos proves who it is, and it says what it may be used for. Each is registered under its
provider — Git, GitHub, AWS or Kubernetes — and owned by a group; whoever holds it decides where it goes, and nobody
else can point it somewhere new.

**Every credential is checked on its own**, whatever it is used for: Lembos asks the system that issued it whether it
still accepts it, and as whom — GitHub or GitLab who a token is, STS who an AWS key or role is, a cluster who its token
is. So each says where it was issued: a token its host, an SSH key its host, a cluster token its API server. A revoked
token shows as revoked on its own page before anything trips over it.

**For targets**, an AWS or Kubernetes credential is named by the targets that authenticate with it. One account key
serves every target in that account: rotating it is one edit, and every target that names it is checked again. Its
page lists those targets, and it cannot be removed while one of them is in service.

**For private sources** — blueprints usually live in private Git repositories or registries — a token, a GitHub App
or an SSH key opens the URL prefixes it lists: every repository or registry path under them. The most specific prefix
wins, so one repository can have a credential of its own. Lembos checks a credential where it is used as soon as you
say where that is, and again whenever it is rotated. A GitHub App's key never leaves the platform: each fetch gets a
short-lived, read-only token for one repository.

## Blueprints

<Screenshot name="blueprints" ratio={3} alt="The blueprints: environment, component and resource recipes, each with its provisioner, latest version and status." />

Each blueprint version pins:

- **What it builds** — a component, a resource, or an environment.
- **The tool** — Terraform, which builds into an AWS account, or Helm, which deploys into a cluster — and the
  exact version of it, chosen from that tool's published releases.
- **The source** — a Git repository or OCI registry, optionally pinned to a digest.
- **Its inputs and outputs** — what it asks for, who may answer each input (the product team or the
  environment), and what it promises back.

<Screenshot name="blueprint-versions" ratio={2.6} alt="A blueprint's versions: 2.6.0 published and current, 2.5.0-rc.1 a draft, 2.4.0 and 2.2.0 deprecated, and 2.3.0 withdrawn because its artifact cannot be found." />

### The version lifecycle

A version starts as a **draft**, where you can edit it and import its inputs and outputs from the module
itself. It can be **published** only once Lembos has fetched its source from the fleet that will run it —
a version that cannot be retrieved is never handed out.

A published version never changes. To change a golden path, publish a new version. Nothing pinned to the old
one moves until its owner moves it, and the Portal shows where each version is still in use. Older versions
can be **deprecated** (still usable, discouraged) or **withdrawn** (no longer offered).

## Artifacts

An **artifact** is a specific built thing — an image, a chart — identified by its content digest, with a
record of where it was built from. A pipeline registers each build after it pushes it; see
[Publish from CI](/docs/use/ci). An artifact can be quarantined, which stops it from being deployed
anywhere.
